# Fixtura Members Subdomain — Route Architecture

## Overview

This document defines the full route structure for the Fixtura members subdomain application.

The application is split into two route groups:

- `(public)` → accessible without authentication
- `(auth)` → requires authenticated session

---

## Core Rule

> Any route that must be accessible before authentication belongs in `(public)`.

> Any route that requires a valid session belongs in `(auth)`.

---

# (public) — Unauthenticated Routes

## Purpose

The `(public)` group handles:

- user entry into the members system
- authentication flow
- support and system state pages
- design system reference (kitchen sink)

---

## Routes

### `/`

**Members Entry Page**

Responsibilities:

- orient the user
- explain this is the Fixtura Members area
- provide a primary sign-in CTA
- provide a help/support CTA

---

### `/sign-in`

**Start authentication flow**

Responsibilities:

- capture email
- initiate OTP / magic link flow

---

### `/verify`

**Complete authentication**

Responsibilities:

- accept verification code or token
- validate login attempt
- redirect to authenticated routes on success

---

### `/auth-error`

**Authentication failure state**

Responsibilities:

- display invalid or expired token/code state
- provide retry path
- link back to `/sign-in`

---

### `/session-expired`

**Session timeout state**

Responsibilities:

- inform the user their session has expired
- provide a clear re-login path

---

### `/help`

**Access support**

Responsibilities:

- explain common login/access issues
- guide users toward recovery steps
- provide support direction

---

### `/maintenance`

**System unavailable state**

Responsibilities:

- display downtime or maintenance messaging
- provide retry guidance

---

### `/kitchen-sink`

**Public design system reference**

Responsibilities:

- display approved UI patterns
- act as the visual source of truth
- support design and component consistency

Card patterns

### `/kitchen-sink/toasts`

### `/kitchen-sink/forms`

Form layout and field patterns

### `/kitchen-sink/dialogs`

Dialog and modal patterns

### `/kitchen-sink/tables`

Table structure and styling

### `/kitchen-sink/popovers`

Popover and overlay patterns

### `/kitchen-sink/loading`

Loading indicators and skeletons

Input controls and field states

## Public Layout (`(public)/layout.tsx`)

### Responsibilities

- provide a minimal branded shell
- maintain consistent spacing and typography
- support all public routes uniformly

### Includes

- Fixtura logo / wordmark
- optional "Members" label
- centered content container
- minimal footer (support, privacy, terms)

### Excludes

- authenticated app navigation
- sidebar
- protected account controls

---

# (auth) — Authenticated Routes

## Purpose

The `(auth)` group contains all protected member functionality.

These routes require:

- valid JWT session
- middleware-controlled access

---

## Business Routes

### `/dashboard`

Primary landing page after login

Responsibilities:

- account overview
- key actions
- recent or important member information

---

### `/settings`

Application and user settings

Responsibilities:

- preference management
- system/user-level configuration

---

### `/bundles`

Content bundles area

Responsibilities:

- view weekly bundles
- preview/download content packs
- manage bundle access

---

### `/template-builder`

Template builder

Responsibilities:

- create/edit templates
- manage branding/layout rules

---

### `/media-gallery`

Media gallery

Responsibilities:

- browse generated media
- filter/search assets
- manage downloads

---

### `/manage-sponsors`

Sponsor management

Responsibilities:

- add/edit sponsors
- manage sponsor placements and usage

---

### `/season`

Season management

Responsibilities:

- configure active season
- manage season-level data/settings

---

### `/account`

Account area

Responsibilities:

- manage user/account details
- organisation/account-level controls

---

### `/logout`

Log out route/action

Responsibilities:

- terminate session
- clear auth cookies/session state
- redirect to `/sign-in`

---

## Auth Layout (`(auth)/layout.tsx`)

### Responsibilities

- provide the authenticated application shell
- support persistent navigation
- support session-aware UI

### Includes

- app header/navigation
- account controls
- protected page layout structure

### Excludes

- public entry UI
- pre-authentication flows

---

# Behaviour Rules

## 1. Strict separation

- `(public)` → no auth required
- `(auth)` → auth required

---

## 2. Authentication flow is public

- sign-in
- verify
- auth-error
- session-expired

These always live in `(public)`.

---

## 3. Kitchen sink is public

`/kitchen-sink/*` is a public route group and should not require authentication.

---

## 4. Middleware controls access

- no UI-based protection
- no client-side auth gating as source of truth

---

## 5. Redirect behaviour

- unauthenticated access to `(auth)` routes → redirect to `/sign-in`
- authenticated access to `/` may redirect to `/dashboard` if desired

---

## 6. Kitchen sink is authoritative

All UI must:

1. be defined in `/kitchen-sink`
2. be reused consistently
3. not introduce new patterns without definition

---

# Summary

The Fixtura members subdomain is structured as:

- `(public)` → entry, authentication, support, maintenance, kitchen sink
- `(auth)` → protected business/member routes

This keeps the system clear, predictable, and aligned with the design/system rules.
