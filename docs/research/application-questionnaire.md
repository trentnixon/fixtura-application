## What it is

### What is the Application?

The repository calls it the "Fixtura Members Application", an account-scoped application for Fixtura members. Its sign-in page says: "Sign in to your Fixtura Members account to manage competitions, branding, and weekly content." A member selects an organisation workspace, sets up its branding and content preferences, inspects competition data and bundle history, manages sponsors, and handles its billing. Sources: `CONTEXT.md`; `src/app/(public)/sign-in/page.tsx:9`; `src/components/navigation/app-sidebar/_constants/sidebar-nav.ts`; `src/lib/config/account-routes.ts`.

The root `README.md` still calls this a marketing site. That wording conflicts with the current glossary and authenticated organisation routes, so it is not a reliable product description. Sources: `README.md`; `CONTEXT.md`; `src/lib/config/account-routes.ts`.

### What is the Application responsible for?

It owns the member-facing organisation workspace, guided organisation setup, account-scoped forms and previews, competition inspection and refresh requests, bundle status and links, billing interactions, and sign-in/profile controls. Its API routes are a frontend proxy to the CMS, rather than the implementation of the competition scraper or weekly production workers. Sources: `src/components/navigation/app-sidebar/_constants/sidebar-nav.ts`; `src/lib/api/routes/route-definitions.ts`; `src/lib/strapi/server.ts`; `.comms/archives/route-hardening/onboarding/12-frontend-integration-guide.md`.

The CMS/backend is the separate `Fixtura.com.au/Backend` repository. Setup workers, authoritative billing/access decisions, and content production belong there. The Application submits requests and reads results. Sources: `.comms/archives/route-hardening/onboarding/12-frontend-integration-guide.md`; `.comms/onBoarding/app-handoff-onboarding-lifecycle-v1-integration.md`; `.comms/accounts/fixtura-billing-frontend-pdr.md`.

### Which jobs stay on the marketing website?

Marketing is a sibling repository named `fixtura/marketing`. The Application's analytics documents distinguish `marketing_site`, `app`, and `hub`. This repository does not establish a complete, current list of marketing website responsibilities. I don't know its exact ownership of registration, public pricing, or lead capture from current Application code alone. Those questions belong to `fixtura/marketing`. Sources: `CONTEXT.md`; `.comms/handoff/analytics-handoff.md`.

### What is the Delivery Hub?

It is the external bundle/asset destination called "Asset Hub" in the Application's "Bundles" UI. The Application constructs links to an account, a specific render, or a render grouping using `NEXT_PUBLIC_BUNDLES_HUBS_URL`. A later handoff identifies its repository as `contentv2`, the Delivery Hub. Sources: `src/lib/config/bundles-hub.ts`; `src/app/(members)/o/[accountId]/bundles/_consts/index.ts`; `.comms/handoff/posthog-hub-identify-handoff.md`.

### Which responsibilities belong to the Delivery Hub rather than the rest of the Application?

The Delivery Hub is a separate codebase, not an implemented section of this Application. This Application owns bundle history, delivery schedule/status, render detail, and the handoff link. The destination experience belongs to `contentv2`. I don't know its complete viewing, downloading, sharing, authentication, or rerun rules from this repository, and do not infer them from the link. Sources: `.scratch/posthog-app-analytics/spec.md`, "Out of scope"; `.comms/handoff/posthog-hub-identify-handoff.md`; `src/lib/config/bundles-hub.ts`; `src/app/(members)/o/[accountId]/bundles/_components/bundles-render-detail-summary.tsx`.

## How the work happens

### What are the onboarding steps after an account is created?

1. "Organisation and permission" selects organisation type, association and, for a club, club linkage; the member confirms authority to act and permission to fetch data. Sources: `src/app/(members)/create-organisation/_components/create-organisation-wizard.tsx`; `src/app/(members)/create-organisation/_components/wizard-step-organisation.tsx`.
2. "Branding" chooses a premade theme or custom branding and supports uploading/cropping the organisation logo. Source: `src/app/(members)/create-organisation/_components/wizard-step-branding.tsx`.
3. "Contact and delivery" collects contact name and the weekly assets delivery email. The UI marks first name and delivery email required. Source: `src/app/(members)/create-organisation/_components/wizard-step-contact.tsx`.
4. "Review and confirm" presents saved organisation, permission, branding and contact details, then calls onboarding confirmation. This review is the member's own review. Source: `src/app/(members)/create-organisation/_components/wizard-step-review.tsx`.
5. Confirmation completes the wizard and requests background preparation through the CMS. Initial setup and initial data fetch have separate statuses. The current Application allows dashboard entry once the wizard is complete, with a pending setup banner; "Vision" remains locked until `isSetup` is true. Sources: `.comms/onBoarding/app-handoff-onboarding-lifecycle-v1-integration.md`; `src/lib/onboarding/resolve-account-entry.ts`; `src/components/scoped-onboarding-sync-banner.tsx`; `src/app/(members)/o/[accountId]/season/_components/season-onboarding-shell.tsx`.

The backend worker belongs to `Fixtura.com.au/Backend`; this answer stops at that boundary. The Application also provides setup polling/recovery and retry after failure. Sources: `.comms/archives/route-hardening/onboarding/12-frontend-integration-guide.md`; `src/app/(members)/create-organisation/setup/setup-client.tsx`.

### What has to be true before the Application will generate content?

This repository does not itself implement the production generation eligibility decision. I don't know the full gate. It establishes these related conditions:

- Organisation setup requires a supported self-service sport and CMS lookup linkage, authority and data permission. Sources: `src/app/(members)/create-organisation/_components/create-organisation-wizard.tsx`; `src/app/(members)/create-organisation/_components/wizard-step-organisation.tsx`.
- The member supplies branding choices and contact/delivery data, then confirms setup. Sources: `src/app/(members)/create-organisation/_components/wizard-step-branding.tsx`; `src/app/(members)/create-organisation/_components/wizard-step-contact.tsx`; `src/app/(members)/create-organisation/_components/wizard-step-review.tsx`.
- "Account ready" in the handoff means successful initial setup and initial data fetch, with `isSetup` true. The active-status UI permits changes only with `isSetup` true and both initial statuses `completed`. This proves an activation-control rule, not the entire renderer's gate. Sources: `.comms/onBoarding/app-handoff-onboarding-lifecycle-v1-integration.md`, section 4; `src/app/(members)/o/[accountId]/account/_utils/account-active.ts`.
- A configured scheduler is needed for the Application to show scheduling data, but the account's scheduler may be null. Sources: `.comms/data-fetching/handoff/done/handoff-phase-05-accounts-scheduler.md`; `src/app/(members)/o/[accountId]/bundles/_components/bundles-delivery-schedule-section.tsx`.
- The backend owns paid access decisions. A displayed plan or completed wizard does not prove content generation is authorised. Source: `.comms/accounts/fixtura-billing-frontend-pdr.md`, section 1.

I could not find a current compatibility matrix for competition providers, a definitive mandatory-logo rule for production generation, or a staff onboarding-approval step in this Application. "Review and confirm" is performed by the member. Any human review policy and final competition/branding/billing gate must be answered by `Fixtura.com.au/Backend` or the operational team, not inferred here. Sources searched: the wizard files above; `src/types/api/account.ts`; `.comms/onBoarding/app-handoff-onboarding-lifecycle-v1-integration.md`.

### How does a weekly pack get from competition data to the member?

The Application-visible sequence is:

1. The member selects an organisation, completes setup, and saves branding/content preferences. Sources: `src/lib/onboarding/resolve-account-entry.ts`; the onboarding wizard above; `src/app/(members)/o/[accountId]/settings/_components/account-settings-preferences.tsx`.
2. "Vision" reads the data already loaded by the backend and offers scoped refresh requests. Competition, grade and fixture-result requests are separate queued actions. Source: `src/app/(members)/o/[accountId]/season/_components/_hooks/use-season-sync-actions.ts`.
3. The member can save a "Bundle delivery day" and a "Bundle delivery profile". Sources: `src/app/(members)/o/[accountId]/settings/_components/account-settings-preferences.tsx`; `src/app/(members)/o/[accountId]/notifications/_components/notifications-form.tsx`.
4. The actual scrape, schedule execution, production render and email sending belong to `Fixtura.com.au/Backend`. This repository reads scheduler `Queued`/`isRendering` and render completion/email flags; it does not implement those jobs. Sources: `.comms/archives/route-hardening/onboarding/12-frontend-integration-guide.md`; `.comms/data-fetching/handoff/done/handoff-phase-05-accounts-scheduler.md`; `.comms/data-fetching/handoff/done/handoff-phase-08-accounts-render-detail.md`.
5. "Bundles" shows returned history and render detail, with asset links and an "Asset Hub" handoff. The Hub experience belongs to `contentv2`. Sources: `src/app/(members)/o/[accountId]/bundles/_consts/index.ts`; `src/lib/config/bundles-hub.ts`; `.comms/handoff/posthog-hub-identify-handoff.md`.

I don't know the backend's exact weekly production order, provider fetch cadence, guaranteed delivery time or email contents from this repository. A selected weekday is a target shown by the UI, not a delivery guarantee. Source: `src/app/(members)/o/[accountId]/settings/_components/account-settings-preferences.tsx`.

### What prices, passes, or billing rules does the Application enforce?

The current purchase is called "Create Season Pass". The member selects a backend-provided tier, chooses a start date, chooses payment method, and reviews the purchase/request. Tier name, price, currency, duration and optional weekly price come from the API. Sources: `src/app/(members)/o/[accountId]/billing/create/create-subscription-wizard.tsx`; `src/app/(members)/o/[accountId]/billing/_components/plan-tier-card/_utils/buildPlanTierCardDisplay.ts`.

I found no authoritative hard-coded $520/year or $650/year price rule. I don't know the live Season Pass or Association Pass prices or the full shorter-pass catalogue. The source displays `price`, `currency`, `daysInPass` and optional `priceByWeekInPass`; it does not reconcile public marketing figures. Authoritative tier pricing belongs to the CMS in `Fixtura.com.au/Backend`. Sources: `src/types/api/account.ts`, `AvailableBillingTier`; `.comms/accounts/fixtura-billing-frontend-pdr.md`, sections 1 and 4.4; `src/app/(members)/o/[accountId]/billing/_components/plan-tier-card/_utils/buildPlanTierCardDisplay.ts`.

Implemented frontend rules include:

- Start dates must be today or later. The UI estimates an inclusive pass end as start date plus `daysInPass - 1`; the backend confirms the authoritative window. Sources: `src/app/(members)/o/[accountId]/billing/create/_components/SelectStartDateStep.tsx`; `src/app/(members)/o/[accountId]/billing/_utils/create-subscription/passEndDateFromWizardStart.ts`; `.comms/accounts/fixtura-billing-frontend-pdr.md`, section 4.5.
- Card payment redirects to a backend-created Stripe checkout. An invoice request is an alternative workflow and has submitted/review state. Source: `src/app/(members)/o/[accountId]/billing/create/create-subscription-wizard.tsx`; `src/app/(members)/o/[accountId]/billing/create/_components/InvoiceRequestSubmittedState.tsx`.
- "Start free trial" advertises 14 days and no payment required. Visibility requires the trial action and organisation trial presentation `start_available`. The Application handles `TRIAL_ALREADY_CONSUMED`, missing organisation linkage and disabled allocation responses. These express backend eligibility, not a new trial for every newly created account. Sources: `src/app/(members)/o/[accountId]/billing/_constants/trial/billingTrialStart.ts`; `src/app/(members)/o/[accountId]/billing/_hooks/useBillingTrialStart.ts`.
- Checkout UI recognises backend action flags, but its compatibility helper also permits checkout when flags are missing or empty. The backend remains authoritative. Source: `src/app/(members)/o/[accountId]/billing/_utils/create-subscription/checkoutActionGate.ts`.
- Turning "Organisation status" off is distinct from ending a paid pass. Its confirmation copy says billing continues, a render already in progress finishes, and missed time is not replayed after reactivation. Execution of those rules belongs to the backend. Source: `src/app/(members)/o/[accountId]/account/_constants/account-active.ts`.

I don't know taxes, refunds, automatic renewals, cancellation economics, coupon validity, or complete pass-based feature restrictions from this repository. Those require the backend's billing rules. Source for that ownership boundary: `.comms/accounts/fixtura-billing-frontend-pdr.md`, section 1.

### What should we know about the Application that these questions did not ask?

One user login can access multiple owned organisation account rows. Each workspace route uses `/o/[accountId]/...`. "Account" in this data model therefore needs care: user identity and organisation account are different things. This repository does not establish team invitations or shared member administration. Sources: `src/types/api/account.ts`; `src/lib/account/account-me-rows.ts`; `src/lib/config/account-routes.ts`; `.comms/archives/route-hardening/onboarding/12-frontend-integration-guide.md`.

There is also a staff "Support accounts" area. It requires a support capability and uses customer read-only browsing restrictions, including restricted Vision actions and hidden template/logo navigation. It should not be described as a member's admin feature. Sources: `src/app/(members)/support/accounts/support-accounts-guard.tsx`; `src/lib/support/support-capability.ts`; `src/components/navigation/app-sidebar/_constants/sidebar-nav.ts`; `src/lib/support/use-season-hub-queries-enabled.ts`.

The member can choose whether junior surnames appear on generated assets, and sponsor position/target allocation is a first-class product concept. Those are concrete editorial controls worth preserving in the video project's knowledge. Sources: `src/app/(members)/o/[accountId]/settings/_components/account-settings-preferences.tsx`; `CONTEXT.md`; `src/lib/sponsors/position-slots.ts`.

Analytics records distinguish marketing, Application and Hub, and client capture requires consent. That cross-product measurement does not make the Hub part of this codebase. Sources: `CONTEXT.md`; `src/lib/analytics/hub-handoff.ts`; `.scratch/posthog-app-analytics/spec.md`.
